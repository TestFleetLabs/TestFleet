# TestFleet — Milestone 2: Test Configuration

## 1. Purpose

Milestone 2 makes everything configurable that a run needs: projects, registries, test definitions, environments with their variables, and schedules. Nothing executes yet; that is Milestone 3.

The data model is defined in section 6 of [tech-architecture-execution-spec.md](tech-architecture-execution-spec.md) (the "main spec"). This document records the decisions the main spec leaves open: UI structure, validation, secret handling, and schedule computation.

Authentication is deferred (main spec, Milestone 1). All pages are open.

---

## 2. Slices

Built and reviewed one at a time, in this order:

| # | Slice | Depends on |
|---|-------|-----------|
| A | Projects | – |
| B | Environments and environment variables (encrypted) | A |
| C | Registries (encrypted password, "Test connection") | – |
| D | Test definitions | A |
| E | Schedules (`next_run_at`, timezone/DST) | A, B, D |

Each slice brings its context, schema, migration, LiveViews, and tests, and passes `mix precommit` on its own.

## 3. UI Structure

```text
/projects                                   list
/projects/new                               form
/projects/:slug                             project page with three sections:
                                              test definitions, environments, schedules
/projects/:slug/edit                        form
/projects/:slug/environments/new            form
/projects/:slug/environments/:env           environment page: variables
/projects/:slug/environments/:env/edit      form
/projects/:slug/test-definitions/new        form
/projects/:slug/test-definitions/:id/edit   form
/projects/:slug/schedules/new               form
/projects/:slug/schedules/:id/edit          form
/registries                                 list
/registries/new                             form
/registries/:id/edit                        form, with "Test connection"
```

- Forms are separate LiveViews (`ProjectLive.Form`), as generated by Phoenix 1.8, not modals. A form knows where it came from and returns there.
- Deleting asks for confirmation (`data-confirm`). Deleting a project deletes its test definitions, environments, variables, and schedules (`on_delete: :delete_all`). Once runs exist (Milestone 3), a project with runs cannot be deleted; that rule arrives with runs.
- Lists use LiveView streams.

## 4. Identifiers

- **Projects** have a unique `slug`, used in URLs and in the API (`POST /api/projects/:project/runs`).
- **Environments** have a `slug` unique per project (`production`, `staging`). It is what `TestFleet_ENVIRONMENT` contains.
- **Test definitions** get a `slug` unique per project. The main spec's API example (section 40) names a test definition by slug (`"test_definition": "customer-portal-e2e"`), but the table in section 6 has no slug column. This milestone adds it; the main spec is updated.
- Slugs are generated from the name when left empty, are lowercase `a-z0-9-`, and can be edited. They are validated, not silently rewritten, when entered by hand.

---

## 5. Encryption at Rest

Environment variable values and registry passwords are encrypted with `cloak_ecto` (`Cloak.Ciphers.AES.GCM`) through a vault, `TestFleet.Vault`.

```text
prod   CLOAK_KEY environment variable (base64, 32 bytes), required at boot
dev    fixed key in config/dev.exs
test   fixed key in config/test.exs
```

Key rotation (a second key, `retired` tag, re-encryption task) is left for later; the vault configuration already supports several ciphers.

A key is generated with:

```bash
mix run -e "32 |> :crypto.strong_rand_bytes() |> Base.encode64() |> IO.puts()"
```

## 6. Environments

- `max_concurrent_runs` is required, 1..100, and defaults to **1**. A new environment is protected by default; raising the limit is a deliberate choice. The global limit (main spec section 34) applies on top.
- The environment page lists its variables and holds the add/edit form for them (section 7).

## 7. Environment Variables

- **Key:** `^[A-Za-z_][A-Za-z0-9_]*$`, unique per environment. Keys starting with `TestFleet_` (case-insensitive) are rejected (main spec section 12).
- **Value:** any string, may be empty for non-secrets.
- **Secret:** a flag per variable. Secret values
  - must be at least 6 characters (main spec section 21: shorter values cannot be masked reliably),
  - are never sent to the browser after saving: the list shows `••••••`, and the edit form shows an empty field with "leave empty to keep the current value",
  - cannot be turned back into non-secrets without entering a new value.
- Variables are edited on the environment page: one form above the list adds a variable, or edits the one chosen in the list (highlighted while editing). Deleting asks for confirmation.
- Secret values are redacted before they are streamed or put into a form, including the form of a failed save, and the value field is redacted from `inspect` output.

## 8. Registries

- `host` is what image references are matched against (main spec section 38): `registry.company.com`, `ghcr.io`, `localhost:5055`, `docker.io`. Unique. No scheme, no path.
  - Stored the way `ImageRef` reports hosts: trimmed, lowercase, and `index.docker.io` as `docker.io`. Otherwise a registry could never match.
  - `Registries.get_registry_for_image/1` resolves the credentials for an image; Milestone 3 uses it when building the execution request.
- `name`, `username`, and `password` are required.
- `password` is encrypted and never sent back to the browser; the edit form works like secret variables: empty means "keep the current password". What the user typed is echoed back while editing (the browser has it anyway); the stored password never is.
- **Test connection** calls the Docker Engine's `POST /auth` with the credentials. This authenticates against the registry without pulling. The socket proxy needs `AUTH=1` for this.
  - Available on the new and the edit form, before saving. It uses the values in the form; an empty password on the edit form uses the stored one.
  - It runs asynchronously; the result is shown in the form and cleared as soon as a field changes.
  - Docker's error message is shown as-is (e.g. `login attempt to http://localhost:5055/v2/ failed with status: 401 Unauthorized`).

## 9. Test Definitions

- `image`: validated with `TestFleet.Execution.Docker.ImageRef.parse/1`.
- `command`: argv array (main spec section 6). The form has a textarea with one argument per line; empty means the image's own entrypoint.
- `timeout_seconds`: required, default 1800, 1..86400. The form shows minutes.
- `cpu_limit`: optional, > 0 (fractional CPUs allowed).
- `memory_limit`, `shm_size_bytes`: stored in bytes; the form uses MiB. `shm_size_bytes` defaults to 2 GiB.
- `enabled`: default true. Disabled definitions cannot be run or scheduled.

---

## 10. Schedules

- Belong to a test definition and an environment of the **same project** (validated).
- `cron_expression`: standard 5-field cron, parsed with the `crontab` library.
- `timezone`: IANA name (`Europe/Vienna`), validated against the timezone database (`tz` library, configured as Elixir's `:time_zone_database`).
- `overlap_policy`: `skip` (default), `queue`, `allow`.
- `next_run_at` (UTC) is computed on create, on every edit of cron expression or timezone, and when a schedule is re-enabled (main spec section 28):
  - the next occurrence is computed on local wall-clock time in the schedule's timezone, then converted to UTC,
  - a local time that does not exist (spring forward) moves to the first valid instant after the gap,
  - a local time that occurs twice (fall back) uses the first occurrence.
- Disabled schedules keep `next_run_at` but are ignored by the tick (Milestone 5).
- The form previews the next three run times in the schedule's timezone while typing.

---

## 11. Done

Milestone 2 is done when all five slices are merged, `mix precommit` passes, and a project with a registry, a test definition, an environment with secret and non-secret variables, and a schedule can be configured entirely through the UI.
